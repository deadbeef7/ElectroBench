# ElectroBench PSP

Scenes 2 (the dusk ocean) and 4 (the power-line corridor) rebuilt on the PSP's
fixed-function Graphics Engine. There are no shaders on the GE, so both scenes
are re-derived from the desktop sources instead of translated:

* `psp/src/psp_scene2.cxx` does the wave field, cloud shadows, fresnel and sea
  palette per vertex in float code; the GE's blend units carry the reflection
  and glitter passes additively. The six-sine wave field is evaluated on the
  VFPU's vector pipeline four waves at a time (`psp/src/psp_waves.hxx`: two
  `vsin.q`/`vcos.q` and three `vdot.q` per vertex), and the per-vertex
  `atan2f`/`asinf`/`acosf`/`powf` calls are replaced by the polynomials and
  integer powers in `psp/src/psp_fastmath.hxx`.
* `psp/src/psp_scene4.cxx` bakes the static pole-line geometry (poles, arms,
  insulators, transformers, houses, walls, trees, pylons, road) into one
  indexed vertex array with per-vertex lighting from `object_frag.glsl`'s
  terms, draws the cables as `GU_LINES`, uses the GE's linear fog for the dusk
  haze, and generates the sky as a CPU-baked equirect panorama plus an additive
  sun sprite.

The HUD uses the same 8x8 atlas as the Vita and Android ports.

## Build

```sh
export PSPDEV=/usr/local/pspdev
export PSPSDK=$PSPDEV/psp/sdk
export PATH=$PSPDEV/bin:$PATH
make -C psp            # -> psp/EBOOT.PBP
make -C psp check-math # host test: fast trig and packed wave constants
make -C psp clean
```

Needs a pspdev toolchain (`psp-gcc`, `mksfo`, `pack-pbp`, `psp-g++`).

`sh buildtools/check_codegen.sh` (from the repo root) asserts that the built
`psp_scene2.o` still contains the VFPU quad instructions; it also checks the
Vita objects' NEON, so build both ports first. Neither the PSP nor a PSP
toolchain that can execute code is available on the build host, which is why
the math that the VFPU kernel replaced is tested on the host instead.

## Hardware use

| Resource | Used for |
| --- | --- |
| VFPU, quad pipeline | wave field (4 waves/instruction), sea colour and reflection math |
| VFPU, scalar pipeline | every other float operation; trig LUT with linear interpolation |
| Graphics Engine | 16-bit 480x272 double-buffered framebuffer, 16-bit depth, additive blend passes, linear fog, textured sky/sun/HUD |
| 2 MB EDRAM | one draw + one display colour buffer and the depth buffer at offsets 0 / 512 KiB |
| 333/333/166 MHz | set at startup, the maximum the hardware allows |

Not used: the Media Engine (no PSPSDK loader on this toolchain, and there is no
separable DSP work in either scene) and the 4 MB volatile RAM (both scenes fit
in main RAM, so a second allocator would add risk without a measured win). The
PSP has a single Allegrex core, so `src/jobs.hxx` is not part of this port.

The icon is a 144x80 palettised PNG generated by `psp/tools/make_icon_psp.py`
from the shared mark in `buildtools/make_icons.py` -- the same drawing the Vita
LiveArea and Android launcher use.

## Status

`EBOOT.PBP` runs both scenes in the same order as the Vita/Android builds:
scene 2 for 45 s, its result panel, scene 4 for 45 s, then scene 4's result
panel and exit. `SELECT` ends the current scene early, `START` quits. The
combined fps report is appended to `ms0:/ElectroBench-psp.txt`.

Both scenes are initialised before the first timed frame, so scene 4's geometry
bake (the largest single piece of CPU work in either scene) is never charged to
a scene's average. Scene 4's static vertex budget is 25,420 of 60,000 vertices
and 46,890 indices; the build prints the counts at startup.

Scene 4's approximations, all forced by the GE:

* lighting is baked per vertex with the sun the run starts under. `SunDirNow()`
  moves its azimuth by only 0.004 rad/s and clamps its elevation at 0.15, so
  over a 45 s run the error is under a 5650 quantisation step.
* the wet-surface reflection of the road/ground is a constant warm term rather
  than a per-pixel grazing reflection (there is no view vector to bake with).
  The far field is the GE's linear fog.
* the sky panorama is refreshed a row at a time (one row per frame in scene 4,
  four in scene 2), not in one go: its integral costs ~20 libm calls per texel,
  and a single-frame bake of the whole grid stalled the picture for most of a
  second every time it came round. The 2.9-degree sun disc is a separate
  additive sprite, because a sky grid dense enough to resolve the disc would
  cost a full-screen tessellation every frame.
* cables are one-pixel lines: at 480x272 a 3 cm conductor is sub-pixel, and the
  desktop tube tessellation would cost more vertices than the rest of the scene.

`DATA.PSP` carries a **PRX** (`BUILD_PRX = 1`), not the ELF that earlier builds
packed. The ELF form is what the console rejected with
`The game could not be started. (8002013C)` - see note 7.

Not yet done: the on-screen score matches the GL slabs only approximately (the
GE cannot tone-map per pixel), and performance has only been measured under
emulation, not on hardware.

A scene's run must also leave the display list **finished**. The results-panel
exit once `break`ed between `sceGuStart` and `sceGuFinish`; `sceGuStart` only
enqueues a list (`sceGeListEnQueue`) and has no idea whether the previous one
was closed, so the GE was handed a stream that never ended and the console hung
on the results panel instead of starting scene 4. The loop now completes the
frame (HudDraw, finish, sync, vblank, swap) and only then leaves, and both
scenes get a clean state reset after the clear.

## Bring-up notes (bugs that cost the most time)

These all present the same way - the clear colour appears, nothing else - so
they are recorded here:

1. **GUM's MODEL matrix starts uninitialised.** The GE always transforms by
   world * view * projection. `sceGumLoadIdentity()` on PROJECTION and VIEW is
   not enough; the model stack must be set to identity too (done once in
   `GuInit`), or every draw collapses to a point while the clear still works.
2. **`sceGumPerspective`/`sceGumLookAt` do not draw here.** With this
   toolchain a probe triangle 25 units in front of the eye never appears with
   them, in degrees or radians, while the same matrices loaded by hand with
   `sceGuSetMatrix` render immediately. `SetSceneMatrix()` therefore builds the
   projection and view explicitly (row-vector form: `w' = z`, `z' = z*A + B`
   with near -> 0). Only `sceGumOrtho` is still used, for the sky and HUD.
3. **The depth buffer is inverted-Z: use `GU_GEQUAL`.** `sceGuDepthRange(65535,
   0)` with `sceGuClearDepth(0)` - the pairing every PSPSDK sample uses - means
   nearer fragments carry *larger* depth values. With `GU_LEQUAL` every
   fragment loses against the cleared 0, so any pass that leaves the depth test
   enabled (the entire sea) is silently discarded while the depth-disabled sky
   and HUD still draw. `sceGuDepthMask(GU_TRUE)` *disables* depth writes, so the
   opaque body pass takes `GU_FALSE` and the additive passes `GU_TRUE`.
4. **`sceGumOrtho` takes (left, right, BOTTOM, top).** Passing `(…, 1, -1, …)`
   draws clip-space y=+1 at the bottom of the screen, which flips the whole sky
   and puts its sun in the wrong place.
5. **Do not copy textures into VRAM with `sceGuCopyImage`.** The GE samples
   textures straight out of main RAM, which is what the PSPSDK `blit` sample
   does (a static RAM array with `sceGuTexImage`). A block transfer with the
   destination/pitch given the wrong way is rejected, and a rejected transfer
   stops the display list, so every draw after it disappears. Textures are
   therefore sampled in place; `sceKernelDcacheWritebackAll()` after rebuilding
   them is all that is needed.
6. `sceGuDrawArray` does not upload GUM matrices; `sceGumUpdateMatrix()` does.
   (Only matters for `sceGuDrawArray`; `sceGumDrawArray` pushes them itself.)
7. **Pack a PRX, not the ELF.** This Makefile originally left `BUILD_PRX`
   unset, so PSPSDK's build.mak packed the stripped *ELF* into `DATA.PSP`
   (its first four bytes were `\x7fELF`). PPSSPP loads that - it sniffs an ELF
   in the PBP - and every emulator screenshot looked fine, so the mistake only
   showed up on a console, where the XMB loader hands that blob to the module
   manager, which cannot read a `~PSP` module header out of it and fails with
   `8002013C` (`SCE_KERNEL_ERROR_LIBRARY_NOTFOUND`). With `BUILD_PRX = 1` the
   link uses `prxspecs` + `linkfile.prx`, `psp-prxgen` emits an `ET_SCE_PRX`
   with a real `.rodata.sceModuleInfo`, and *that* is what `DATA.PSP` holds.
   Check with `psp-readelf -h ElectroBench.prx`: `Type: (ffa0)` is correct; a
   plain `EXEC` means the PBP will not boot on hardware even if it runs in an
   emulator.

   The PRX stays unsigned, which every CFW (PRO/ARK) accepts; only OFW would
   need a Sony key we do not have.
